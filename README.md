# japan-plane-rectangular-cs-zones

日本の平面直角座標系（全国19系）の適用区域ポリゴンデータです。
国土数値情報（行政区域データ）の行政区域に平面直角座標系の系番号を割り当て、系ごとにまとめたポリゴンと、
都道府県・市町村と系番号の対応データをまとめて提供することを目指しています。

> **ここまで進んでいます**: 19系の定義（`data/zones.csv`）、系番号を判定するルール（`data/zone_rules.csv`）、
> 市区町村と系番号の対応表（`data/municipality_zones.csv`）を用意できました。系ごとにまとめたポリゴンは
> 大きい（約164MB）ので、GitHubのReleasesで配ります（下の「系ごとのポリゴン（Releasesで配布）」）。

## 収録データ

### `data/zones.csv` — 19系の定義

平面直角座標系（平成十四年国土交通省告示第九号）の表をそのまま書き写したものです。文字コードはUTF-8（BOMなし）、改行はLFです。

| 列名 | 内容 |
|---|---|
| `zone` | 系番号（1〜19） |
| `zone_roman` | 系番号のローマ数字表記（I〜XIX） |
| `origin_lon_dms` / `origin_lat_dms` | 座標系原点の経度（東経）・緯度（北緯）。告示の値（度分秒） |
| `origin_lon` / `origin_lat` | 同じ値を10進数で表したもの（度） |
| `epsg_jgd2011` | 対応するEPSGコード（JGD2011、EPSG:6669〜6687） |
| `area_text` | 告示にある「適用区域」の文言 |

- 原点と適用区域は、国土地理院のページ「平面直角座標系（平成十四年国土交通省告示第九号）」
  https://www.gsi.go.jp/LAW/heimencho.html （最終改正 平成二十二年三月三十一日国土交通省告示第二百八十九号）から書き写しました。
- `epsg_jgd2011`は告示には出てきません。原点の経緯度と縮尺係数0.9999がEPSGの定義と一致することを、
  pyprojのEPSGデータベースで確認しています（`tests/test_zones_csv.py`）。
- `area_text`は人が読むための文章です。系番号を実際に判定するときは`data/zone_rules.csv`を使います。

### `data/zone_rules.csv` — 系番号の判定ルール

告示にある適用区域を、元データ（行政区域データ）の属性と経緯度から判定できる形に書き直したものです。
UTF-8（BOMなし）、改行はLFです。

| 列名 | 内容 |
|---|---|
| `rule_id` | ルールの番号。この順番で評価し、最初に条件が合ったルールを採用します |
| `zone` | 系番号 |
| `prefecture` | 都道府県名（N03_001と照合） |
| `subprefecture` | 北海道の振興局名（N03_002と照合） |
| `county` | 郡名（N03_003と照合） |
| `municipality` | 市区町村名（N03_004と照合） |
| `code` | 全国地方公共団体コード（N03_007と照合、5桁）。市町村の名前を書いたルールにだけ書きます |
| `lon_min` / `lon_max` / `lat_min` / `lat_max` | 代表点の経度・緯度の範囲（度、JGD2011）。両端を含みます |
| `basis` | 告示のどの部分に基づくか（要約） |
| `note` | 補足や、こちらで置いた仮定 |

- 欄が空のときは「条件なし（どの値でも一致）」という意味です。
- `code`が書いてあるルールは、名前とコードの両方が合ったときだけ当てはまります。北海道の2つの泊村のように
  同じ名前の市町村を取り違えたり、名前とコードが食い違ったりしたときに、テストで気づけるようにするためです。
  コードは元データ（2026年版）の値です。元データの年度を上げるときは、市町村の合併などでコードが変わって
  いないか、`tests/test_n03_attributes.py`で確かめてください。
- 政令指定都市は、元データでは区ごとのコード（例：札幌市中央区は01101）になっていて、市のコードは出てきません。
  政令指定都市全体をコードで指定することはできないので、名前で書きます。
- 告示にある「〜を除く」という書き方は、ルールを上から順に評価することで表しています。例えば東京都の場合、
  先にXIV系・XVIII系・XIX系に当てはまるかどうかを確認し、どれにも当てはまらなければIX系、という順番です。
- 境界線上ぴったりの点は複数のルールに当てはまりますが、その場合は`rule_id`が小さい方を優先します
  （例：東経143度ちょうどはXIV系になります）。
- 判定処理は`scripts/zone_rules.py`に書いています（標準ライブラリだけで動きます）。
- 元データの属性ファイル（.dbf）は`scripts/n03_dbf.py`で読み込みます（これも標準ライブラリだけで動きます）。

**元データと突き合わせて確認できた点**（N03 2026年版の属性ファイル `N03-20260101.dbf`、125,130行）

- ルールに書いた都道府県名・振興局名・郡名・市町村名は、すべて元データにそのままの書き方で出てきます。
- 東京都・鹿児島県・沖縄県以外の行は、すべて属性だけでどれかのルールに当てはまります。
- 告示で名前が挙がっている北海道の市は、どれも想定どおりの振興局に入っています。
- 北海道には「泊村」が2つあります（後志総合振興局と、根室振興局の北方領土）。振興局で区別しているので、
  それぞれ XI系と XIII系に分かれます。
- 島や岩礁は、1つずつ別の行に分かれています（例：小笠原村は4,812行、石垣市は1,214行）。

この突き合わせは、`tests/test_n03_attributes.py` で同じことをやり直せます（「テスト」の節を見てください）。

**まだ仮定のままの点・確認できていない点**

- 東京都・鹿児島県・沖縄県のポリゴンは、系の境目（北緯28度や東経126度・130度など）をまたいでいないことを
  確認できました（2026-10-04、Windows で`scripts/check_coordinate_zones.py`を実行、またぐ候補0件）。
  詳しくは`VALIDATION.txt`を見てください。
- この3都県では、1つの市町村の中で系が分かれるものがあります（小笠原村、薩摩川内市、南さつま市、三島村、十島村）。
  市町村単位の対応表では、こうした市町村に複数の系を書くことになります。
- 鹿児島県の「奄美群島」は、大島郡と奄美市とみなして扱っています（こちらで置いた仮定です）。
  元データの大島郡は11町村（喜界町・龍郷町・大和村・宇検村・瀬戸内町・徳之島町・天城町・伊仙町・和泊町・
  知名町・与論町）で、奄美市と合わせて12市町村です。これが奄美群島と同じ範囲であることは、法令などの
  資料ではまだ確かめていません。

### `data/municipality_zones.csv` — 市区町村と系番号の対応表

全国地方公共団体コードごとに、系番号をまとめた表です（1,905行）。元データ（2026年版）のすべてのポリゴン
（125,130件）に系番号を割り当てて集計しました。UTF-8（BOMなし）、改行はLFです。

| 列名 | 内容 |
|---|---|
| `code` | 全国地方公共団体コード（元データのN03_007、5桁）。政令指定都市は区ごと、所属未定地は都道府県コードに000を付けたもの |
| `prefecture` / `subprefecture` / `county` / `municipality` / `ward` | 都道府県名・北海道の振興局名・郡名・市区町村名・政令指定都市の区名（N03_001〜N03_005） |
| `zones` | 系番号。1つの市町村の中で系が分かれる場合は`;`で区切って書きます（例：小笠原村は`14;18;19`） |
| `polygons` | 元データでのポリゴンの数 |

系が分かれるのは、東京都小笠原村（XIV・XVIII・XIX系）、鹿児島県の薩摩川内市・南さつま市・三島村・十島村
（I・II系）の5件です。どの島がどの系かは、系番号の列を足したシェープファイル（次の節）で確かめられます。

### 注意していただきたいこと

平面直角座標系の適用区域は、多くは都道府県・市町村・振興局の単位で決まっていますが、
次の都県だけは経緯度の範囲で決まっています（告示より）。

| 都県 | 系 | 区分の基準 |
|---|---|---|
| 鹿児島県 | I・II | 北緯27〜32度、東経128度18分〜130度（奄美群島は130度13分まで）の範囲内にある島はI系、それ以外はII系 |
| 東京都 | IX・XIV・XVIII・XIX | 北緯28度より南の部分を、東経140度30分と143度で区分。それ以外はIX系 |
| 沖縄県 | XV・XVI・XVII | 東経126度と130度で区分 |

この3都県では同じ市町村の中でも系番号が分かれることがあり、市町村単位の対応表だけでは
系番号を1つに決められない場合があります。該当する区域の扱いは、データを追加するタイミングでこの
READMEに書き足します。

北海道は、振興局の所管区域と一部の市・町の単位でXI〜XIII系に分かれます。

座標の測量・設計などに使う場合は、国土地理院の資料と根拠となる法令（座標系の告示）で、必ず適用区域を
確認してください。

### 元データについての注意（出典URLのページの「その他の情報」より）

- 一部の市区町村には境界が決まっていない地域があり、元データでは境界線が暫定的に引かれています。
  このリポジトリのポリゴンも、その暫定境界線をそのまま引き継いでいます。境界が決まっていない地域の詳細は、
  該当する市区町村に確認してください。
- 東京都千代田区・中央区・港区の境界と、東京都中央防波堤埋立地は、元データ側で修正が行われています。

### 使用する元データの属性

元データ（行政区域データ2026年版）の属性のうち、次のものを使う予定です。属性名の後ろの括弧内は
シェープファイルでの属性名です。

| 属性名 | 用途 |
|---|---|
| 都道府県名（N03_001） | 系番号の割り当て |
| 北海道の振興局名（N03_002） | 北海道内での系番号の割り当て |
| 郡名（N03_003） | 表示用 |
| 市区町村名（N03_004） | 系番号の割り当て |
| 政令指定都市の行政区名（N03_005） | 表示用 |
| 全国地方公共団体コード（N03_007） | 対応表のキー |

全国地方公共団体コードは、元データの定義では任意項目（多重度0..1）ですが、2026年版ではすべての行に入っていました。
同じコードに別の名前が付いている行もありませんでした。

元データには、市区町村が決まっていない「所属未定地」の行があります（東京都123行、鹿児島県12行など）。
これらは市区町村名が「所属未定地」、コードが都道府県コードに000を付けたもの（例：東京都は13000）になっています。
系番号は、都道府県の単位のルール（東京都・鹿児島県・沖縄県では経緯度のルール）で決めます。

## 経緯度で系が分かれる都県の確認

東京都・鹿児島県・沖縄県のポリゴンが系の境目をまたいでいないかは、`scripts/check_coordinate_zones.py`で調べます。
元データのシェープファイル（`.shp`と、同じ名前の`.dbf`）を読み、ポリゴンごとの範囲（最小・最大の経度と緯度）と、
その範囲に入る系をCSVに書き出します。標準ライブラリだけで動くので、QGISやGDALがなくても使えます。

PowerShellでは、リポジトリのフォルダで次のように実行します（パスはご自分の環境に合わせてください）。

```powershell
python scripts\check_coordinate_zones.py "C:\path\to\N03-20260101.shp" coordinate_zones.csv
```

Bashでは次のとおりです。

```bash
python scripts/check_coordinate_zones.py /path/to/N03-20260101.shp coordinate_zones.csv
```

- 判定ルールの境目は、どれも経線か緯線です。ポリゴンの範囲をその線で区切り、区切った部分ごとに系を求めます。
  すべて同じ系ならそのポリゴンの系（`zone`列）が決まり、違う系が混ざれば「またぐ候補」（`crosses_boundary`が`yes`）になります。
- 「またぐ候補」は範囲で見た結果です。ポリゴンそのものは境目をまたいでいないこともあるので、QGISで形を見て確かめます。
- 書き出したCSVはUTF-8（BOMなし）です。Excelで開くと文字化けすることがあります。
- 実行すると、都県ごとの系の件数と「またぐ候補」の件数が画面に出ます。
- ファイルの指定を間違えたとき（`.dbf`を指定した、パスに「...」が残っている、`.dbf`が同じフォルダにないなど）は、
  「エラー:」で始まる短い説明が出ます。

## 対応表と系ごとのポリゴンの作り方

### 1. 系番号を割り当てる

`scripts/build_zone_data.py`は、元データのすべてのポリゴンに系番号を割り当て、次の2つを書き出します。
標準ライブラリだけで動きます。

- `municipality_zones.csv`：対応表（`data/municipality_zones.csv`と同じもの）
- `<元の名前>_zone.shp`など：元データのシェープファイルに`ZONE`列（系番号）を足したもの。形は元のままです

OSGeo4W Shellでは、リポジトリのフォルダで次のように実行します（パスはご自分の環境に合わせてください）。
書き出し先は、元データとは別のフォルダを指定します。

```bat
python scripts\build_zone_data.py "C:\path\to\N03-20260101.shp" output
```

東京都・鹿児島県・沖縄県で、系を1つに決められないポリゴン（境目をまたぐもの）があると、「エラー:」と出て止まります。
2026年版では、そのようなポリゴンはありませんでした（`VALIDATION.txt`）。

### 2. 系ごとにまとめる（ディゾルブ）

系ごとに1つのポリゴンにまとめる処理は、形の計算が必要なので、QGISで行います。

1. QGISで`output\N03-20260101_zone.shp`を開きます。
2. メニューの「ベクタ」→「空間演算ツール」→「ディゾルブ」を開きます。
3. 「ディゾルブの基準とする属性」で`ZONE`を選び、出力をGeoPackage（`.gpkg`）に保存します。

2026年版では、QGIS 3.44.11で約1分40秒かかり、19件（系ごとに1件）のマルチポリゴンができました。
GeoPackageの大きさは約164MBでした（`VALIDATION.txt`）。形が正しくないポリゴンがあるというエラーは出ませんでした。
もしエラーで止まったときは、先に「ベクタ」→「ジオメトリツール」→「ジオメトリの修復」をかけてから、ディゾルブしてください。

**注意**：ディゾルブの結果には、`ZONE`のほかに`N03_001`〜`N03_007`の列も残ります。これは、それぞれの系に
まとめられたポリゴンのうち、1つの値がたまたま残ったもので、意味がありません（例：IX系の行に、ある1つの
市区町村の名前が入る）。配るときは「ベクタ」→「属性テーブル」→「フィールドの削除」で、`ZONE`以外の列を
消してください。

## テスト

リポジトリのルートで実行します（Python 3.9以降を想定。標準ライブラリだけで動きます）。

```bash
python -m unittest discover -s tests -v
```

pyprojが入っていない環境では、EPSGの定義と照合するテストはスキップされます（未実行として扱ってください）。

元データとの突き合わせ（`tests/test_n03_attributes.py`）は、元データをリポジトリに入れていないので、
環境変数`N03_DBF`に`N03-20260101.dbf`のパスを指定したときだけ動きます。指定しなければスキップされます。

```bash
N03_DBF=/path/to/N03-20260101.dbf python -m unittest discover -s tests -v
```

PowerShellでは次のように指定します。

```powershell
$env:N03_DBF = "C:\path\to\N03-20260101.dbf"
python -m unittest discover -s tests -v
```

`tests/test_zone_rules.py`にある地点ごとの期待値は、告示の適用区域から導いたものです。代表点の経緯度は
おおよその位置で、元データとの照合はまだ行っていません。
